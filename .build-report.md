## What was tested / verified

- `python3 -m py_compile` on every module: clean.
- `ruff check custom_components tests`: clean (default ruleset).
- Full local test run: **18/18 passed**, 0 warnings, in a real `.venv`
  (`homeassistant==2026.2.3`, `pytest-homeassistant-custom-component==0.13.316`, installed via
  `tests/requirements_test.txt`, unpinned so pip resolves a fitting HA core version
  transitively — this is the standard approach for this test package).
- The `test_setup_entities.py` end-to-end test exercises the real `async_setup_entry` path
  (bootstrap+states mocked via `aioclient_mock`, WS `start()` mocked to avoid a real network
  connection attempt from the background task) and confirms: device created with correct
  identifiers/manufacturer, both sensor entities registered with the exact
  `unique_id = f"{sensor_id}_{type}_{channel or ''}"` scheme, correct `device_class`/unit for
  `WATER_TEMPERATURE`/`WATER_PH`, entity state reflects the polled value, and
  `async_unload_entry` completes cleanly.
- `venv`, `.pytest_cache`, `__pycache__` are excluded via `.gitignore` and were not committed.

## Deviations from the literal file list

- **ws.py had to land together with `__init__.py`** in the "core" commit rather than as its own
  later commit, because `__init__.py` imports `HydroNodeWebSocketClient` at module level —
  landing them separately would leave an intermediate commit with a broken import. Commit order
  used: scaffold → core (api/coordinator/ws/config_flow/__init__) → entities → tests → docs.
- Added `tests/test_setup_entities.py` beyond the three explicitly named test files, to get
  end-to-end coverage of device/entity creation and unload, which the three named files don't
  individually cover.
- `manifest.json` includes `"integration_type": "hub"` (optional modern-manifest field, not in
  the spec but recommended by current HA manifest conventions for a cloud-polling hub with
  multiple devices) and `documentation`/`issue_tracker` URLs pointing at the (not-yet-existing)
  `TexhFexLabs/hydronode-homeassistant` GitHub repo, matching the org used elsewhere in the
  design doc's assumptions.
- `include_followed` option is actually wired into entity/device filtering (`filter_stations()`
  used in `__init__.py`, `sensor.py`, `event.py`) rather than left as an inert config knob, since
  an option that doesn't change behavior would be dead weight.
- Follow/unfollow REST endpoints (`POST`/`DELETE /api/stations/public/{id}/follow`) and PAT
  CRUD (`/api/user/api-tokens`) were intentionally **not** implemented in `api.py` — the task's
  file list only asked for `bootstrap()` and `states()`, and the design doc explicitly places
  command/management entities ("Befehls-Entities … Später (out of scope v1)") out of v1 scope.
  Token creation/revocation is documented in the README as a `curl` workflow instead.

## Open items / follow-ups (not done, for awareness)

- No `strings.json` (source-of-truth for HA's translation tooling) — shipped
  `translations/en.json`/`de.json` directly, which is the common pattern for HACS repos without
  a Lokalise/build pipeline; if the repo later gets an HA-core-style translation pipeline this
  should be revisited.
- No CI workflow (`.github/workflows/*`) was added — out of scope per the task's file list, but
  worth adding (`ruff` + `pytest` + `hassfest`/`hacs` validation actions) before a public HACS
  submission.
- `manifest.json`'s `documentation`/`issue_tracker` URLs assume the GitHub repo will be created
  at `TexhFexLabs/hydronode-homeassistant`; update if the actual org/repo differs.
- Real end-to-end testing against a live HydroNode backend (`curl`/`wscat` per the contract doc)
  was not performed — this was a from-scratch build against the documented contract only, no
  running backend was available/targeted in this task.
